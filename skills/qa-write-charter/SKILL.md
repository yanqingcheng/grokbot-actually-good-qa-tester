# Write the charter (with the manager, before testing)

**When:** a test request has arrived and testing hasn't started yet. Before the manager confirms, you may do only what the charter needs: the access check, the readiness checks (smoke-running your tools and proving the rest of what the mission needs), and reading. Testing itself (probes) starts after the manager confirms. **Next:** [qa-run-test-session](../qa-run-test-session/SKILL.md) once the manager confirms.

## Brief and setup questions

Testing starts here, before you touch the product (see [What is testing](../what-is-testing/SKILL.md)). Question the brief, the requirements, the plan, the setup and everyone's assumptions. A problem you can see in the request itself (missing target, unreachable environment, contradictions, no users or quality bar) is a finding: raise it with the manager now.

## Steps

Start by re-reading your setup answers (memory and `setup.md`). If anything they rest on has changed since they were written (house rules, the manager's instructions, the project), bring `setup.md` up to date now and note what changed. Note the version of these skills you are using (their version lines; re-check at confirm time). Then apply the target, accounts and independence rules in [qa-tester-test-session](../qa-tester-test-session/SKILL.md): named target and access, quick signed-out access check, approved test accounts only.

1. **Who matters for this session.** Take the project's who-matters list from setup and check it against the brief: add anyone new the brief brings up (and update the saved list), mark guesses as guesses, and write down which of those people this session tests for and what each would reasonably expect from this target. Where the product has agent users or stakeholders (bots that browse, call the API, parse its pages or data, or act for a person), plan for them on equal terms with humans: work out what they would reasonably do, and include those actions in scope (examples: a search crawler or AI agent reading the page, a browsing agent filling in a form for a person; and, among people, a person using a screen reader). Bugs are measured against those expectations, not only against the spec. If there is no saved list yet, draft one from the brief and send it to the manager with the charter to confirm (or to whoever your house rules name); until it is confirmed the list counts as guesses, and safe work goes ahead. If the list changes after the charter is confirmed, follow step 7 of [qa-run-test-session](../qa-run-test-session/SKILL.md).
2. From the request, draft the charter with the manager: **project name** (used for folder names), **target**, **mission / what to test** (charter sentence: "Explore [target], with [resources], to discover [risks]"), **scope in / out**, **quality goals** (intent / acceptance notes), **heuristics picked** from [exploratory-testing-techniques](../exploratory-testing-techniques/SKILL.md) (oracles, tours, attacks, data heuristics), **pre-approved risky probes**, **timebox** (sized to the mission and agreed with the manager: short rounds are normal for checks, re-tests and validation; there is no minimum) and target settings (start from your defaults from setup). The charter plans for a successful session (see [qa-tester-test-session](../qa-tester-test-session/SKILL.md)): say which user actions are in scope (see "user action" in [qa-tester-test-session](../qa-tester-test-session/SKILL.md); examples: pages, controls, widgets and flows), at which target settings, and the quality bar for what users do, not only static checks. If the timebox can't cover them, say what's left out and agree it with the manager now.
3. **Ask about scope and quality goals when the request doesn't make them clear.** Ask the manager what's in and out of scope (features, areas, target settings, known-rough or unfinished areas, won't-fix) and what quality bar matters at this stage (core flow works, looks right on mobile, no data loss, speed, accessibility, fun, ...). Asking is always allowed; once the charter is confirmed, open questions don't block safe probing that's clearly in scope. Tailor the heuristics to the answers. Don't spend effort on out-of-scope areas. Anything you notice there anyway is noted separately, in `notes.md` and the report's noticed-but-out-of-scope list, and reported to the manager; it doesn't get one of this project's BUG-NNs. A problem in the skills or tools you are testing with is different: it isn't out-of-scope product behaviour but a bug in another project, so write it up there as [write-bug-report](../write-bug-report/SKILL.md) says.
4. Mark every planned probe safe or risky (risky-probe gate in [qa-tester-test-session](../qa-tester-test-session/SKILL.md)). Put the risky ones in the charter's gate list (what / where / why / worst case / undo).
5. **For each change under test (or write "no change: exploratory"), write down what would actually exercise it** (the input or state that makes the new code path run) rather than what only checks that nothing regressed. If the bug depends on a timing window (a lock, claim, timeout, debounce, cache expiry), name the window in the charter: what starts it, how long it lasts, and where that number comes from.
6. **Plan and get resources** as [qa-tester-test-session](../qa-tester-test-session/SKILL.md) describes, and fill in the charter's Readiness section. If anything material is missing, ask the manager for it, or for a narrower charter, in the confirmation request (step 9).
7. Create the session folder in your evidence folder (from setup) and write `charter.md` (template: `references/templates.md`, which also has the `notes.md` format). If `<evidence folder>/<project>/setup.md` doesn't exist yet, write it now.
8. **Self-review before sending.** Check the charter against its goals and what a good charter looks like. Could this charter reach a successful session: does it name the user actions in scope at each target setting, and does the quality bar include what users do, not only static checks? Does it name who matters for this session (checked against the project list, new people added, guesses marked) and what they would expect, and a target you have confirmed is reachable (with the access-check result written down: reachable, reachable with the browser check deferred, or unreachable)? Does it say what would actually exercise each change? Is the Readiness section filled in ("Plan and get resources" in [qa-tester-test-session](../qa-tester-test-session/SKILL.md)): everything the mission needs listed, each item proven or recorded as missing with evidence, and anything material asked for or the charter narrowed? Did you raise the brief and setup questions? Does it name the actor for each risk it evaluates, and, for any security risk that needs forced or forged input, name that risk and actor and put those probes in the gate list ("Input must match the actor" in [qa-tester-test-session](../qa-tester-test-session/SKILL.md))? Is every risky probe in the gate list? Is there a timebox? Would a reasonable manager understand it and agree? Every answer must be written in `charter.md` itself, not only in your head; the template has a place for each, and if your answer has no place, add a line. Fix anything you find before sending.
9. Ask the manager for a quick confirmation before testing starts, even if the request looked complete. Send a **short** summary (illustration: about five lines) covering the mission, who it tests for, the quality bar, heuristics, target settings and readiness (anything missing and what you need). With it, send the path to `charter.md`, every gate request in full, and anything still waiting for confirmation (for example an unconfirmed who-matters list). Wait for the confirm; silence is not a yes. Once confirmed, move to [qa-run-test-session](../qa-run-test-session/SKILL.md): safe probes can start, and each risky probe waits for its own okay. A pending okay blocks only the probes it covers, unless the mission depends on them (then it is a material gap: readiness step 4 in [qa-tester-test-session](../qa-tester-test-session/SKILL.md)).
10. If the request is a checklist of expected answers with no goal, people who matter or quality bar, ask the manager for those before testing. Never turn a checklist line-for-line into your runner's prompt; a passing checklist is not a green judgement.
