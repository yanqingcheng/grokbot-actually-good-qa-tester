> **Read [What is testing](../what-is-testing/SKILL.md) first** (what testing and a bug are; question the brief before touching the product). General rules for every phase: [qa-tester-test-session](../qa-tester-test-session/SKILL.md).

# Run the test session

**When:** the charter is confirmed, with its readiness section showing the mission can be met (risky probes only once okayed). Write each bug once, in full, the moment you find it, with [write-bug-report](../write-bug-report/SKILL.md); later only add to that entry. **Next:** [qa-review-evidence](../qa-review-evidence/SKILL.md), before any verdict.

1. **Notes first.** Keep `notes.md` running with `date +%T` timestamps: every action, expectation, observation (exact text, timings, visual state, console/network errors if visible), hunch, and small weirdness. **Don't pre-filter: when in doubt, write it down.** Log observation times, not the time you wrote the line. **Write each line as it happens, with the time read from a clock at that moment** (for example `date +%T`, or your script printing the time next to each step); never fill times in later from memory or file dates. If you must reconstruct a time, mark it as reconstructed (for example `~17:25 (reconstructed from file time)`) and treat it as tester-reported. Keep the notes in time order. The report's story comes from these notes, not memory.
2. **Record what happens, with a clock you can trust**, using **your recording setup (from setup)** (for a website, a screen recording with a clock burned in). Take any lease your house rules require first. Your recording setup and any fallback were proven and chosen at readiness ("Plan and get resources" in [qa-tester-test-session](../qa-tester-test-session/SKILL.md)); here you only check that the actual capture starts and plays (a few seconds, checked for example with `ffprobe`) and re-check anything that may have changed since. If something fails, it is a readiness gap: pause the work that depends on it and tell the manager straight away what failed. Switch only to the fallback agreed at readiness; if no equal fallback works, follow readiness step 4 (ask for the resource or an agreed scope change). On a headed desktop, use a screen grab like the example below; for a headless browser, use the automation tool's own video and log the clock time of each event from your script (those times are tester-reported unless a clock is visible in the video). **Whatever records, every clip needs a way to turn a point in the video into a clock time:** a clock in the picture, or the clock time the clip started (logged in `notes.md` at that moment) so that start time plus video time gives the clock time. Read every reported time off the video clock when there is one, otherwise from your script log (tester-reported), never from a subagent's estimate. Example for an X display, with ffmpeg started in the background (the screen size, display and font path are only examples; replace them with your own recording setup):
   ```
   cd <evidence folder>/<project>/<YYYY-MM-DD>; nohup ffmpeg -loglevel error -f x11grab -video_size 1280x800 -framerate 10 -i "$DISPLAY" -vf "drawtext=fontfile=/usr/share/fonts/truetype/dejavu/DejaVuSansMono-Bold.ttf:text='%{localtime\:%H\\\\\:%M\\\\\:%S}':x=w-tw-10:y=10:fontsize=22:fontcolor=yellow:box=1:boxcolor=black@0.7" -c:v libx264 -preset ultrafast -pix_fmt yuv420p -y video/rec-01.mp4 > video/rec-01.log 2>&1 & echo $! > video/rec-01.pid
   ```
   Test the overlay once on a short smoke clip, after stopping the recording as in step 8: render a single frame to a png (`-frames:v 1`) and look at it. Prefer several short clips (`rec-02`, …) per probe group over one long one.
3. **Open look first.** Before any specific checks, look at every affected surface and what a user can do there (examples: each page, dialog, menu and embedded widget), at every target setting (the charter's, or your defaults from setup), as each of the charter's users, and write down anything that looks wrong, clipped, misaligned or unfinished. This unscripted pass comes before scripted probes. As you look, list in `notes.md` every user action in scope (see "user action" in [qa-tester-test-session](../qa-tester-test-session/SKILL.md)): everything the people and agents who matter can do, **or can reasonably believe they can do** from what the product shows them. Something that invites an action and then does nothing is a finding. Examples: a "press start" prompt, an image or text styled as a button, a game or player inside a page, hover menus, Back and Forward, a keyboard shortcut the page mentions. Success needs each one tried at each target setting **the way that user would, with input that user could really give (see "Input must match the actor" in [qa-tester-test-session](../qa-tester-test-session/SKILL.md)), not by a shortcut that skips how they get there**; mark each as you try it, with the result, or why not.
4. **Drive the product with narrow probes**, one focused goal per call (e.g. "enter a 10,000-char name in the signup form, submit, report exact on-screen result and any console errors"), either through your driver or by scripting it yourself. If you script it, your script log is the transcript of what was done; still keep the list of user actions in `notes.md` as the coverage list of what was tried and what wasn't (it may point into the log for detail). Ask the driver to report exactly what it saw. Never claim something was tested without actually doing it: for an interactive target, driving it; for a target you test by reading (skills, documents, a process), reading the exact version yourself.
   - Your driver acts only through the means the actor really has: no forced clicks, no dispatched or injected events, no acting on a control no real means reaches, unless the charter is evaluating a named security risk (see "Input must match the actor" in [qa-tester-test-session](../qa-tester-test-session/SKILL.md)). If an action fails, never force it: record the failed attempt, then find out whether it's the product or your driver by repeating the same means through another driver ("Tool or product?" in that section). If that works, it's a tool problem. If only a different means the actor has works, the original failure still stands for that means, and the other route is a workaround to report alongside it.
   - Give it an **explicit allow-list** of the controls and keys it may use, never a deny-list with exceptions.
   - **The subagent never chooses answers, grades, or other submitted values.** When a probe must submit values, you specify the exact values: the exact text to type and the exact button to press for every submission (for example "type `Ada Lovelace` in Full name, press Save"). If the page needs a choice you didn't specify, it stops and reports.
   - **Submission guard.** A runner that misreads the screen submits wrong data for real (for example by mistaking one field for another, misreading a similar-looking character, or making a typo).
     - In your instructions, give the on-screen context the value belongs to and the exact keys (for example "Field labelled `Full name` under `Billing details`: type `Ada Lovelace`").
     - Before submitting, the runner reads back the on-screen context (labels, prompt, surrounding text). It submits only if that matches your instructions; otherwise it stops and reports without submitting.
     - After submitting, the runner reports the app's response before taking any further action. If the response differs from what you expected, it stops and reports.
5. **Capture evidence at key moments** (screenshots, or for things a screenshot can't show, the console or network log): each bug, odd states, and the main passing states. Prefer contact sheets (many shots tiled into one image) over a small fixed shot cap, and personally open the key shots before judging any area green. Look with your screenshot tool (or the automation tool's screenshot); save a file into the folder (example, adapt to your setup: `ffmpeg -loglevel error -f x11grab -video_size 1280x800 -i "$DISPLAY" -frames:v 1 -y shots/NN-<slug>.png`), or extract a frame from the recording. Log each path in `notes.md`. Check every saved frame matches its label (right tab active, right state) before you cite it.
6. **Evidence and timing rules** (apply as you go, not at report time):
   - **Every finding needs evidence that fits its target, and a time.** For an interactive target, that is a capture (step 5). For a target you test by reading, it is the source version (commit, revision or date), the location (file and line, section or step), the exact quotation and when you read it; add a screenshot or recording only when it shows something the quotation can't (illustration: how the text renders). A finding counts as confirmed only with both evidence and time. If one is missing, keep what you have, report it as unconfirmed and say exactly what is missing (for example "screenshot, no time"); with neither, it is "seen once, no evidence". Never drop it.
   - **Define every timed interval** by the event that starts it and the event that ends it, both as clock times (for example "close = the tab leaves the tab strip; request = Enter pressed on the new URL; shown = the card text renders"). Never report a bare duration.
   - **Timing-window bugs:** for each try, log the gap against the named window and mark it **in** or **out**. Only in-window tries count toward FIXED. Out-of-window tries are reported separately as regression coverage, because the old code would probably have passed them too. If a path stalls long enough to wait out the window (a long blank or spinner), mark that try out as well. Measure how long your own driver really takes between actions before relying on it for a short window; if it's too slow, pre-stage the second action (illustration: pre-type the URL in a spare tab and send the close and Enter as one key sequence), then measure the real gap on the video.
   - **Review the whole recording, not just the counted tries.** Mis-clicks and setup accidents can produce the exact state under test; time them and report them like any other try.
   - **Log every write the session submits** (save, form submit, answer, grade, override) with its time, the value (secrets by reference only, see "Test accounts" in [qa-tester-test-session](../qa-tester-test-session/SKILL.md)), the app's verdict if any, whether it overrode that verdict, and who chose it (your instruction or the subagent).
   - **Link checks** (every address the product points people to): report each link as OK, broken or unknown. A link is **broken** only when the site clearly says the page is gone or wrong (for example 404 or 410, or a dead domain). When a site blocks or limits automated checks (for example 429 too many requests, 403 forbidden, 999, a captcha or "are you a robot" page), count it as **unknown, not broken**, say why, and give the three counts separately. Check an unknown link once by hand in the browser if it matters; don't retry fast to get past the block.
   - **Claims ledger:** for each finding, add a line to the Claims ledger section of `notes.md` marking each time or fact as **video-verified**, **server-verified** or **tester-reported** (for example what a browser helper said).
7. Work the charter's heuristics; follow hunches ("bugs cluster"). If something risky comes up mid-session, stop and run the risky-probe gate (qa-tester-test-session), and carry on with safe work meanwhile.
   **If the who-matters list changes mid-session** (someone confirms or corrects it, or you find a new person who matters): update the project list in `setup.md`, add a timed "Charter change" line to `charter.md` (what changed, who said so, and what it changes for this session), and re-plan the remaining time. If it changes the mission, scope or quality bar, tell the manager in one line and carry on with safe work while you wait; don't silently rewrite the charter.
8. **Stop recording:** `kill -INT "$(cat video/rec-01.pid)"` (INT so the mp4 finalizes). Stop only the process you started, by its own pid: never by a name or file pattern, which can match another session's recorder. Save the recorder's own pid when you start it (for example `$!` straight after starting ffmpeg itself, not a wrapper shell). If the file keeps growing after the stop, find the pid that is writing *your* file by its full path in your session folder (`ps -o pid,args`), check it is yours, and stop that pid; if you can't be sure, tell the manager instead. Wait until that pid has exited (for example `while kill -0 <pid> 2>/dev/null; do sleep 0.5; done`) before touching the file; only then check it really plays by decoding all of it (`ffmpeg -v error -i video/rec-01.mp4 -f null -`; no output means it decoded) and read its length (`ffprobe -v error -show_entries format=duration -of csv=p=0 video/rec-01.mp4`).
9. **Optional:** have a video-review helper (for example a watchVideo subagent) review a clip (from a folder your video reviewer can read) for things you missed: flicker, layout jumps, slow loads, error toasts. Add its findings to `notes.md`, marked as from video review.
10. **The session ends only when the mission is covered (your call, with evidence), when the timebox runs out (with evidence of the times), when the manager says stop, when you and the manager agree to end it, or when you reject the mission (Mission Rejected, below)**; being blocked is never a reason to end it on your own; write which in `notes.md`, naming the stopping heuristic you used from `references/stopping-heuristics.md` of [qa-tester-test-session](../qa-tester-test-session/SKILL.md) (Michael Bolton's list, adapted), with what wasn't covered and what risk remains. **It pauses when the mission can no longer be met** with what you have (something material missing, broken, or with no equal fallback): stop the affected work, ask the manager for the resource or an agreed scope change, and resume only when the revised mission can be met. **A gap that needs a resource or a change of scope is pause and ask, never follow-up work;** only items outside this charter's scope, or left untried when the session ends in one of the ways below, become follow-up work. Waiting time is logged and doesn't count against the timebox; research, planning and reflection do count, because they are part of testing. The timebox is the most time you have, not a target to fill (see "What a successful session looks like" in [qa-tester-test-session](../qa-tester-test-session/SKILL.md)).
   - **Mission covered:** every in-scope action tried to its end at each target setting, with evidence, and depth spent where the risks call for it, so that more time would add little. Write why you stopped and what risks remain.
   - **Out of time:** the timebox agreed in this charter ran out, shown by the start time and the timed notes. Waits (for a lease, a tool, a resource or a decision) are logged separately and don't count; research, planning and reflection during the session are part of testing and do count.
   - **Blocked means pause and ask, not stop:** nothing left in scope can be tried. You made reasonable, cheap, permitted attempts with the tools available to you and none worked. Pause as above: ask the manager for the resource or an agreed scope change, and keep doing any work that doesn't depend on it. The session ends on a block only when the manager agrees to end it or says stop; record that agreement with its time. "My current driver can't" is not blocked until you've tried the obvious alternatives (illustrations: a headed browser instead of headless, another recorder, your platform's reference recipes, asking the manager). Record what you tried, and why any other option doesn't suit (too slow for the time left, risky, or it would change the agreed setup; ask the manager before changing the setup).
   - **The manager says stop,** or **an end is agreed** with the manager (record who agreed and when).
   - **Mission rejected:** you decline work because carrying on would cause a problem for someone, especially an ethical one (Mission Rejected in the stopping heuristics). Stop that work at once and tell the manager why. If the rejection covers the whole mission, the session ends there; otherwise carry on with in-scope work it doesn't affect while the manager decides.
   - **Paused:** see above; a pause is not a stop, and work that doesn't depend on the missing item carries on meanwhile.
   Passed checks, "the main things work", "I've named what's left" or an untested assumption are never reasons to stop. **Use the time in this order:** (1) the charter's "User actions in scope", line by line, at each target setting (the charter's list, not just your own); (2) once every line is tried, depth on those same actions, led by risk: repeats (especially anything flaky), variants, and abuse (illustrations: double clicks, reload or Back mid-action, extremes of a slider). Keep going while more depth would still tell the people who matter something worth knowing, within the timebox. An action counts as tried only when you went through it **to its end the way that user would**: the product's own sign that it is finished, or the point where the user would reasonably give up (illustration: a puzzle until the site says it is solved, a game until it ends or is paused and resumed, a form until its confirmation). For each action still untried, give the reason it can't be tried in this session; those become follow-up work in the report.
11. **Wind down for the evidence review:** stop recordings and any helper you no longer need, using their pid files (every background process you start writes one in the session folder). You may keep (or reopen) the browser or dev server the review will need (missing shots, a before/after comparison). The full **Resource cleanup** in [qa-tester-test-session](../qa-tester-test-session/SKILL.md) runs at the end of [qa-review-evidence](../qa-review-evidence/SKILL.md), before the report.

The notes.md format is in `references/templates.md` of [qa-write-charter](../qa-write-charter/SKILL.md).

## Anti-patterns

- "Looks fine" with no evidence (screenshots, for an interactive target); claims of testing without driving the product (or, for a reading-only target, without reading the version cited); reaching a state by a shortcut instead of the way a user would (for example loading a page by its URL instead of clicking to it); skipping something that invites an action because it might be decoration; forcing an action the actor couldn't take (see "Input must match the actor" in [qa-tester-test-session](../qa-tester-test-session/SKILL.md)).
- Pre-filtered notes; times written down later instead of as they happened.
- Ending the session in any way other than those in step 10; calling the mission covered while some in-scope action could still be tried, or on an assumption you haven't proven (when the timebox, the manager's stop or an agreed end comes first, the session ends incomplete and says so); turning a gap that needs a resource or a scope change into follow-up work instead of pausing to ask; calling a gap "named" instead of closing it; calling something blocked or a tool limit without proving it.
- Softening attacks that the charter's risks call for on a safe target. (Attacks are tools: choose them by the charter, the risks and the approvals, not all of them every time.)
- Letting a driver subagent pick submitted values; leaving submitted writes or overrides out of the notes.
- Counting out-of-window tries toward FIXED; reporting durations without start and end events; trusting a subagent's time estimate over the video clock.
